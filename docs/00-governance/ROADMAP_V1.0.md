## 1. 对题目的专业分析

### 1.1 课题性质

本课题首先是软件工程类工程设计，其次才是算法应用研究。答辩价值来自业务闭环、系统架构、数据一致性、角色协同、实验方法和可追溯证据的组合，而不是提出新的预测算法或训练新的大模型。

系统由三条主线构成：

- 业务主线：需求—计划—订单—供应商—到货—收货—对账；
- 工程主线：权限、状态机、事务、数据接入、审计、部署与测试；
- 智能主线：需求预测、采购建议、文本结构化解析和异常解释。

### 1.2 课题的合理边界

V1.0 面向“单采购企业、多供应商”的校内演示场景，不做多租户 SaaS。所谓多源数据融合，落地为带来源标记、批次审计和质量报告的 CSV 适配器原型；论文必须明确这不是已经连接真实 ERP、SRM 的生产接口。

对账只覆盖采购订单、实际收货数量、单价和金额差异的业务确认，不扩展到发票、税务、付款或财务总账。物流只记录预计到达、运输状态和异常，不连接真实承运商。

### 1.3 “数智化”如何成立

- 数字化：统一数据模型、线上状态流转、供应商数据隔离、审计与看板；
- 智能化：可复现的需求预测、确定性补货建议、大模型文本解析；
- 安全性：算法和大模型都只提供建议，业务变更必须经校验与人工确认；
- 可研究性：预测模型和 Prompt 策略均设置基线、数据集、指标和实验记录。

### 1.4 明确不采用的错误路线

- 不把大语言模型当作数值时序预测器；
- 不用 LLM 输出直接修改订单、库存或对账状态；
- 不为了“先进”堆砌微服务、Kafka、Kubernetes、区块链或知识图谱；
- 不先编造论文数据，再反向拼接系统截图；
- 不把模拟数据或演示回放描述成真实企业生产数据。

## 2. 核心创新点

本项目固定三个可落地创新点，不宣称算法理论创新。

### I-01 可追溯的多源供应链数据规范化

设计供应商、物料、库存、历史需求和计划事件的统一数据模型，为不同来源模板建立字段映射、批次号、来源系统、校验错误和导入日志。价值在于让后续预测、采购和看板使用同一口径，并能追溯每条数据从何而来。

### I-02 预测驱动的采购建议闭环

使用 7 日移动平均建立基线，使用 XGBoost 结合滞后、滚动、日历和已知计划事件特征进行需求预测。预测结果不直接下单，而与现有库存、在途数量、安全库存、采购提前期和最小采购量共同形成可解释建议，再由采购人员确认进入计划和订单。

### I-03 大模型结构化事件解析与人在回路控制

仅支持采购需求、计划变更和到货通知三类白名单意图。文本先由大模型按固定 Schema 解析，再经过结构校验、业务规则、数据库事实校验、影响预览和用户确认，最后由 Spring Boot 事务落库。全过程保存原文、模型、Prompt、原始输出、规范化结果、错误和确认人。

可作为工程亮点但不单列创新：订单—到货—收货—对账的可审计状态机和异常事件看板。

## 3. 系统用户与业务场景

### R-01 系统管理员

- 管理用户、角色、菜单与权限；
- 维护系统参数、字典、AI供应商配置的非密钥部分；
- 查看操作日志和导入日志；
- 不代替采购人员处理正常业务。

### R-02 采购协同人员

- 维护供应商、物料、库存和需求数据；
- 执行预测、查看采购建议并创建需求；
- 使用 AI 解析采购需求和计划变更；
- 创建采购计划与订单；
- 处理到货、收货、库存更新和对账；
- 查看预警并记录处理结果。

### R-03 供应商

- 只能访问绑定 supplier_id 的订单和通知；
- 确认或反馈订单；
- 提交结构化或自然语言到货通知；
- 查看自身交付状态和对账差异；
- 不能查看其他供应商数据、企业成本汇总或系统配置。

### R-04 企业管理人员

- 查看供应链看板、预测指标、供应商交付和异常统计；
- 审批采购计划或高风险异常；
- 查看只读业务明细和追溯记录；
- 不直接维护基础数据。

### 典型业务场景

1. 采购人员导入历史需求和库存数据，系统生成未来 14 日预测与缺货预警；
2. 采购人员确认采购建议或输入自然语言需求，生成待审批计划；
3. 管理人员审批计划，系统创建订单并发送给指定供应商；
4. 供应商确认订单、提交到货通知，延期时触发预警；
5. 采购人员完成收货，系统记录库存流水并生成对账；
6. 管理人员从看板查看预测、履约、库存与异常闭环。

## 5. 最核心业务闭环

业务闭环编号：BCL-01。

历史需求、库存和已知计划事件导入  
→ 数据校验与统一口径  
→ MA7 与 XGBoost 预测  
→ 库存覆盖与确定性缺货规则  
→ 采购建议  
→ 人工确认或 AI 文本解析生成采购需求  
→ 采购计划提交与审批  
→ 采购订单  
→ 供应商确认  
→ 到货通知  
→ 企业收货与库存流水  
→ 订单/实收差异对账  
→ 看板与预警  
→ 新数据进入下一预测周期

### 核心状态机

采购计划：

DRAFT → PENDING_APPROVAL → APPROVED → ORDER_CREATED → CLOSED  
异常出口：REJECTED、CANCELLED。

采购订单：

PENDING_CONFIRMATION → CONFIRMED → PENDING_SHIPMENT → SHIPPED → ARRIVED → RECEIVED → RECONCILING → COMPLETED  
异常出口：REJECTED、CANCELLED。

到货通知：

DRAFT → SUBMITTED → IN_TRANSIT → ARRIVED → RECEIVED  
异常出口：CANCELLED、EXCEPTION。

对账：

PENDING → CONFIRMED → COMPLETED  
差异路径：PENDING → DISPUTED → RESOLVED → COMPLETED。

所有状态只能通过后端状态服务变更，必须校验当前状态、角色、数据范围和 version，记录操作者、前后状态、业务编号和时间。前端隐藏按钮不等于权限控制。

### 异常闭环

- 预测缺货：生成 WARNING，采购人员确认建议或记录不采纳原因；
- 供应商延期：关联订单和到货通知，记录新 ETA 与处理结果；
- 收货差异：保存订单数量、实收数量和差异原因，进入争议对账；
- AI 解析不完整：只展示缺失字段，不允许确认；
- 网络或 AI 服务失败：保留原文，允许改用结构化表单，业务主流程可继续。

## 6. 推荐技术栈与选择原因

### 6.1 技术栈

| 层次 | 选择 | 原因 |
|---|---|---|
| 前端 | Vue 3、TypeScript、Vite、Element Plus、Vue Router、Pinia、Axios、ECharts | 学习和实现成本可控，适合管理后台、角色页面和数据看板 |
| 业务后端 | Java 17、Spring Boot 3.x、Spring MVC、Validation、Spring Security + JWT、MyBatis-Plus、Flyway、OpenAPI | 适合企业业务、事务、权限、状态机、数据库迁移和接口文档 |
| AI 服务 | Python 3.11、FastAPI、Pydantic、pandas、scikit-learn、XGBoost、可替换 LLM Provider | Python 生态适合时间序列特征、实验和结构化解析 |
| 数据库 | MySQL 8.x | 与建议技术路线一致，关系模型和事务适合采购业务 |
| 测试 | JUnit 5、SpringBootTest、pytest、Vitest、Postman/Newman、Playwright | 覆盖单元、接口、AI和核心跨角色流程 |
| 部署 | Docker Compose、Nginx、环境变量与健康检查 | 可在答辩机复现，复杂度低于容器编排平台 |

### 6.2 AI 方案比较

| 方案 | 优点 | 缺点 |
|---|---|---|
| Spring Boot 直接调用 LLM，并在 Java 中做预测 | 服务少、部署简单 | Python 预测和实验生态接入不自然，算法与业务耦合 |
| Spring Boot + 单个独立 FastAPI | 预测、LLM、实验边界清楚；便于复现和替换模型 | 增加一次 HTTP 调用和服务故障处理 |

最终选择第二种。该方案不是微服务群：Spring Boot 仍是唯一业务入口、唯一业务数据读写方和 AI 结果持久化编排者，FastAPI 是不持有业务库凭据的无状态智能能力服务。

### 6.3 暂不引入 Redis

当前数据量和并发不需要缓存或分布式锁。幂等使用业务唯一键、请求幂等号、数据库事务和乐观锁完成。只有性能测试证明存在可重复瓶颈时，才通过 ADR 变更引入 Redis。

## 7. 系统总体架构

### 7.1 逻辑分层

1. 表现层：Vue 管理端和供应商端，共用一套前端工程，按权限生成菜单；
2. 接口与安全层：Spring Security、JWT、参数校验、统一异常、审计；
3. 业务层：基础数据、库存、采购、订单、协同、收货、对账、预警和统计；
4. 智能编排层：Spring Boot 组装业务上下文、调用 FastAPI、验证结果、生成预览；
5. AI 能力层：FastAPI 完成特征计算、预测、Schema 解析和 Provider 适配；
6. 数据层：MySQL 保存唯一业务事实；模型文件和实验产物保存在受控目录；
7. 外部层：可配置的大模型 API；CSV 模板模拟 ERP、SRM、库存和计划数据来源。

### 7.2 调用边界

- Vue 只调用 /api/v1 下的 Spring Boot 接口；
- Spring Boot 通过内部 /internal/v1 接口调用 FastAPI；
- FastAPI 不鉴权终端用户，不直接读取或写入业务 MySQL，也不持有业务库凭据；
- Spring Boot 向 FastAPI 传递带 schema_version、snapshot_id、as_of_time 和 data_hash 的版本化数据快照，并负责持久化返回结果；
- 本地开发时 FastAPI 只监听 127.0.0.1:8001；容器部署时只暴露在 Compose 内部网络的 8001 端口，不由 Nginx 对外转发；
- Spring Boot 使用环境变量中的 X-Internal-Service-Token 调用 FastAPI，令牌不得进入前端、日志或版本库；
- Spring Boot 对 AI 返回再次执行数据存在性、权限、状态和版本校验；
- 外部 LLM 密钥仅通过环境变量进入 FastAPI，不进入前端、数据库或 Git；
- 所有外部调用设置超时，只有幂等请求允许有限重试。

### 7.3 部署形态

答辩部署使用一组 Docker Compose 服务：

- Nginx：提供前端静态资源并转发业务 API；
- Spring Boot：业务服务；
- FastAPI：AI 与预测服务，仅内部可访问；
- MySQL：业务数据库；
- 外部 LLM：通过 HTTPS 调用，若不可用则进入显著标注的降级模式。

### 7.4 后端模块边界

采用模块化单体，不拆多个 Maven 服务。建议包：

- common：统一响应、异常、校验、工具；
- auth：用户、角色、权限、JWT；
- masterdata：供应商、物料、仓库；
- inventory：库存和流水；
- procurement：需求、计划、订单和状态机；
- collaboration：供应商、到货、收货、对账；
- intelligence：AI编排、预测记录、预警；
- dashboard：聚合查询和统计；
- system：字典、日志、导入任务。

## 8. AI 大模型模块方案

### 8.1 白名单任务

AI-01 采购需求解析：

- 物料编码或名称；
- 固定数量、增减数量或增减比例；
- 期望到货日期；
- 供应商等级或指定供应商；
- 优先级和备注。

AI-02 计划变更解析：

- 计划/物料标识；
- 原数量、新数量或数量差；
- 原日期、新日期或提前/延后天数；
- 变更原因；
- 缺失字段。

AI-03 到货通知解析：

- 订单号、供应商、物料和数量；
- 预计到达时间；
- 运输状态；
- 异常情况和备注。

风险说明以确定性计算事实为核心。可选的 LLM 文字润色只能引用已计算指标，不得产生新数值或新决策。

### 8.2 安全处理链

1. 输入长度、字符和任务类型预检查；
2. 将用户文本视为不可信数据，使用白名单任务、固定提示和输入包裹降低 Prompt 注入与越权指令风险；
3. LLM 按指定 JSON Schema 输出；
4. FastAPI 使用 Pydantic 校验类型、枚举和必填项；
5. 规则层校验数量、日期、比例、订单号等；
6. Spring Boot 查询真实物料、供应商、订单、状态和权限；
7. 生成“修改前—修改后—影响—警告”的预览；
8. 用户明确确认；
9. Spring Boot 在事务中落库并写操作日志；
10. 失败时保留原文和错误，不改变业务数据。

LLM 不配置业务写工具、不持有业务库凭据，也不能依赖提示词实现绝对安全；最终安全边界由无写权限、后端校验和人工确认共同保证。自报 confidence 不能作为自动执行依据。信息不足时返回 missing_fields 和 needs_confirmation。

### 8.3 记录内容

ai_parse_record 至少保存：

- task_type、schema_version；
- input_text、context_snapshot；
- provider、model_name、model_version；
- prompt_version、prompt_hash、temperature；
- raw_response、normalized_json；
- schema_valid、business_valid、validation_errors；
- target_type、target_id；
- confirmed_by、confirmed_at、final_status；
- request_id、latency_ms、created_at。

### 8.4 Provider 与降级

建立统一 LLM Provider 接口，具体模型根据合法可用的 API 密钥再锁定。实验开始后固定模型版本、温度和 Prompt，不能中途更换后合并结果。

没有网络或密钥时，演示可使用：

- 结构化手工表单；
- 明确显示 DEMO_FALLBACK 的规则解析或已保存回放。

降级结果不得计入大模型实验，也不能在论文中写成在线模型调用。

### 8.5 AI 解析实验

- 数据集：至少 60 条，目标 72 条人工编制供应链文本；
- 覆盖：正常采购、数量调整、日期调整、计划变更、到货通知、模糊/缺失/复杂表达；
- Ground Truth：人工标注标准 JSON，并进行二次核对；
- 策略 A：普通任务 Prompt；
- 策略 B：结构化 Prompt + JSON Schema；
- 策略 C：结构化 Prompt + JSON Schema + 少量标注示例与明确缺失字段约定；
- 模型提取指标：在执行后置业务规则前，计算 JSON 有效率、必填字段准确率、字段级 Precision/Recall/F1、关键字段完全正确率和延迟；
- 安全链指标：对同一批输出单独统计规则拒绝率、错误放行率、待人工补录率和端到端安全通过率；
- 记录：每条输入、标准答案、实际输出、解析策略、模型信息、错误类型和最终判定；
- 原则：业务规则降低错误放行不得表述为“提高了模型字段识别准确率”；不预设“必须达到”的漂亮结果，若策略差异不明显或效果不佳，如实分析。

## 9. 需求预测模块方案

### 9.1 预测目标

以物料每日真实需求或消耗量为目标，V1.0 的系统页面、采购建议和论文实验统一输出未来 14 日曲线。7日和30日窗口只列为后续可选扩展，不进入 V1.0 验收或论文结果。

### 9.2 数据来源

- 历史需求/消耗记录；
- 日期、星期、月份等已知日历特征；
- 已确认的生产/采购计划变更事件；
- 物料基础属性。

当前库存和在途订单用于预测后的采购建议，不直接作为未来需求标签的替代。所有模拟数据使用固定随机种子和可复现生成脚本，并标注 SIMULATED。

### 9.3 模型选择

基线模型：7 日移动平均 MA7。  
主模型：XGBoost Regressor。

模型粒度固定为逐物料训练：每个满足样本门槛的物料保存一个一步预测 XGBoost 模型，预测时把前一步预测值按相同特征规则递归写入，连续产生未来14日结果。MA7 也使用已观测值与前序预测值滚动生成14日基线。有效日记录少于300天或非零需求日少于60天的物料不训练 XGBoost，直接使用 MA7 并显示回退原因；规划中的模拟实验数据至少覆盖两年日粒度，以满足时间划分和回测要求。

不采用 LSTM 的原因：数据量、调参和解释成本高，不适合当前本科项目。暂不选择 Prophet/ARIMA，是为了把工程投入集中在一个清晰的基线和一个特征型主模型上。递归策略会积累误差，因此论文必须逐预测步展示或讨论误差变化。

### 9.4 特征

- lag_1、lag_7、lag_14、lag_28；
- rolling_mean_7/14/28；
- rolling_std_7/14/28；
- day_of_week、month、is_weekend；
- 仅使用预测时已经知道并经确认的计划事件特征。

滚动特征必须先 shift 再计算，严禁包含当日或未来真实需求。

### 9.5 数据划分与评估

- 每个物料按时间顺序划分训练 70%、验证 15%、测试 15%；
- 验证区间执行三次扩展窗口回测：每次训练截止日向后推进，后接连续14日验证窗口；三次结果用于特征和超参数选择；
- 最后15%的测试区间保持封存，只在模型和参数确定后做一次最终报告；
- 样本不足的物料回退到 MA7，不强行训练 XGBoost；
- 指标以 MAE、RMSE 为主；
- MAPE 只在真实值非零的样本上计算并披露处理方法；
- sMAPE 作为零需求较多场景的补充；
- 主模型若未优于基线，系统允许回退，论文如实报告原因。

### 9.6 采购建议

建议采购量采用确定性公式：

建议采购量 = max(0, 采购提前期内预测需求 + 安全库存 - 当前可用库存 - 在途数量)

再按供应商最小采购量和包装倍数向上取整。每条建议展示预测窗口、库存、在途、安全库存、提前期和取整过程，采购人员可采纳、调整或拒绝，并填写原因。

当采购提前期超过14日时，系统标记 HORIZON_INSUFFICIENT，不把14日结果外推为自动建议；只展示14日参考需求并要求采购人员补充更长周期计划或人工调整。演示数据优先选择提前期不超过14日的供应商。

### 9.7 预测证据

必须保存：

- 原始/清洗数据与数据字典；
- 数据划分边界和随机种子；
- 特征定义、模型参数和软件版本；
- 每次 forecast_run 的时间、物料、指标和模型文件；
- 真实与预测曲线；
- 基线与主模型逐物料对比；
- 失败实验和异常样本，不只保存最好结果。

## 10. 数据库核心表规划

### 10.1 表分组

| 领域 | 核心表 | 作用 |
|---|---|---|
| 用户权限 | sys_user、sys_role、operation_log | 固定角色 RBAC、供应商账号绑定、菜单/接口权限与审计 |
| 基础与库存 | supplier、material、warehouse、inventory、inventory_transaction | 供应商、物料、当前库存余额和收货变更流水 |
| 数据接入 | data_import_batch、demand_history、demand_event | 来源批次、历史需求、已确认计划/需求事件 |
| 采购 | purchase_demand、purchase_plan、purchase_plan_item、purchase_order、purchase_order_item | 从需求到订单的主业务数据 |
| 协同 | delivery_notice、delivery_notice_item、receipt、receipt_item、reconciliation、reconciliation_item | 到货、收货和差异对账 |
| 智能 | forecast_run、forecast_result、ai_parse_record、warning_record | 预测、解析、建议来源和预警 |
| 审计 | operation_log | 操作人、前后状态、请求号、业务对象和错误 |

### 10.2 关键关系

- sys_user 可选绑定 supplier_id；供应商角色查询必须强制带该范围；
- supplier、material、warehouse 是库存和采购业务的主数据；
- inventory 明确定义为当前库存余额表，以 warehouse_id + material_id 唯一；每次增减都必须有对应 inventory_transaction；
- purchase_plan 由一个或多个 purchase_demand 汇总，purchase_plan_item 指向 material；
- purchase_order 由已审批 purchase_plan 生成，并保存供应商；
- delivery_notice、receipt、reconciliation 的主表均关联 purchase_order_id；
- delivery_notice_item、receipt_item、reconciliation_item 均显式关联 purchase_order_item_id，不通过物料编码猜测订单行；
- receipt 成功后同一事务写 inventory_transaction 并更新 inventory；
- forecast_result 属于 forecast_run；由预测建议生成的 purchase_demand 记录 forecast_run_id；
- ai_parse_record 通过 target_type/target_id 关联确认后的需求、计划或到货通知；
- warning_record 关联 material、supplier、order 或 forecast_run 中至少一个业务对象。

### 10.3 字段与约束原则

- 主键统一 BIGINT；
- 业务单号使用有唯一索引的 VARCHAR，不把数据库 id 直接暴露为业务号；
- 数量使用 DECIMAL(18,3)，金额使用 DECIMAL(18,2)；
- 状态采用明确枚举值并由服务层状态机控制；
- 所有核心表含 created_at、updated_at、created_by、updated_by；
- 可并发变更的业务表含 version 乐观锁；
- 主数据可软删除，订单、收货、对账、实验和审计记录不得物理删除；
- JSON 只用于 AI 原始结果、错误明细和实验参数，不替代正常关系字段；
- 由文件导入的数据统一使用 import_batch_id 关联 data_import_batch；外部记录通过 source_system + external_id 建立去重约束；
- 外键、唯一键、非空约束和组合索引在数据库设计阶段逐表确认；
- 常用索引覆盖 business_no、status、material_id、supplier_id、date 和 import_batch_id。

### 10.4 建表顺序

RBAC → 基础数据 → 数据接入/需求 → 库存 → 采购计划/订单 → 到货/收货/对账 → 智能记录 → 审计与预警。

## 12. 论文七章分别写什么

### 第一章 绪论

写采购企业与上游供应商协同中的数据分散、预测滞后、文本变更难结构化、状态不可见等具体问题；明确研究目标、三个工程创新点、研究内容和论文结构。国内外研究现状必须在正式检索后写，未核验文献不得进入参考文献。

### 第二章 相关技术

只介绍真实使用的 Vue、Spring Boot、MySQL、JWT、REST、ECharts、XGBoost、时间序列特征、大模型结构化输出、Prompt 和人在回路校验。避免写 Redis、微服务、LSTM 等未实现技术。

### 第三章 系统需求分析

说明四类角色、BCL-01 业务闭环、用例、业务规则、状态约束、数据范围、功能需求和非功能需求。给出多源模板导入的实际边界，不写真实 ERP 在线集成。

### 第四章 系统总体设计

给出总体架构、模块结构、部署结构、数据库 ER、核心表、权限模型、状态机、AI 安全链、预测流程和接口边界。图必须由最终代码结构反向核对。

### 第五章 系统详细设计与实现

围绕登录权限、数据导入、预测与建议、采购计划/订单、供应商协同、到货收货、对账、AI解析、预警和看板展开。每节按目标—设计—流程—实现—页面证据书写，不大段贴代码。

### 第六章 系统测试与实验分析

先写测试环境和策略，再写功能、权限、异常、状态、接口、性能和降级测试；随后分别报告预测实验和 AI 解析实验。所有表格来自保存的原始测试与实验记录，不补造结果。

### 第七章 总结与展望

仅总结实际完成的系统、实验和可验证效果；说明模拟数据、文件式集成、外部模型依赖等局限。展望可写真实 ERP 接入、多批次物流和更丰富模型，但不得表述为已实现。

## 16. 技术风险与规避方法

| 风险 | 影响 | 规避和触发措施 |
|---|---|---|
| 范围失控 | 无法按时形成完整闭环 | 固定 P0 范围和“不做清单”；新增功能必须走 ADR |
| 把计划写成已实现 | 论文失真 | CURRENT_STATUS 只记录可验证事实；所有截图来自运行系统 |
| 把文件导入包装成真实 ERP 接口 | 答辩可信度受损 | 明确“CSV适配器原型”，保存来源和批次 |
| 模拟数据过于理想 | 预测结论失真 | 固定种子；加入趋势、周期、噪声、缺失和异常；公开生成脚本 |
| 时间序列泄漏 | 指标虚高 | 按时间划分；滚动特征先 shift；测试集只使用一次 |
| XGBoost 不优于基线 | 论文结果不符合预期 | 如实报告；按物料分析；系统提供 MA7 回退，不改造数据 |
| LLM 输出错误或注入 | 错改业务数据 | 白名单任务、Schema、规则、DB校验、影响预览、人工确认 |
| LLM 网络/额度不可用 | 演示中断 | 结构化表单与显著标注的回放降级；提前准备离线演示路线 |
| 前后端/AI字段漂移 | 集成失败 | OpenAPI与Schema版本化；契约测试；禁止聊天临时改字段 |
| 状态并发与重复提交 | 重复订单、库存错误 | 唯一键、幂等号、事务、乐观锁、状态迁移服务 |
| 供应商越权 | 数据泄漏 | supplier_id 后端强制范围；越权用例纳入阻断测试 |
| 收货与库存不一致 | 业务事实冲突 | 同一 Spring 事务写收货、库存和流水；失败整体回滚 |
| AI服务与业务服务分布式失败 | 解析记录悬空 | AI只计算不落库；超时后不改变业务；请求号可追踪 |
| 密钥或隐私泄漏 | 安全问题 | 环境变量、示例配置、日志脱敏、模拟/去标识数据 |
| 部署环境不一致 | 答辩机无法运行 | Docker Compose、健康检查、初始化脚本和离线依赖预案 |
| 项目与论文逐渐分叉 | 最终材料自相矛盾 | 每版更新追踪矩阵；论文只引用已验收版本证据 |
| 多会话交接失真 | 重复劳动或推翻基线 | README阅读顺序、CURRENT_STATUS、ADR、CHANGELOG、固定编号 |

## 18. 防止后续交接混乱的总控协议

### 18.1 每次开始

1. 阅读 README 和 CURRENT_STATUS；
2. 查看当前版本的进入/退出条件；
3. 查看 DECISION_LOG 是否已有相关决策；
4. 在 TRACEABILITY_MATRIX 找到该功能编号；
5. 查看 DELIVERABLE_REGISTER 和尚未关闭的 UAT_FEEDBACK；
6. 只处理 CURRENT_STATUS 中的“唯一下一步”或用户明确新增的任务。

### 18.2 每次结束

必须留下：

- 完成了什么，涉及哪些文件；
- 运行了哪些验证，结果是什么；
- 数据库、接口、状态机是否变化；
- 新增测试、截图和论文证据编号；
- 已知问题、未完成项和唯一下一步；
- 是否需要更新 ADR、追踪矩阵、交付物登记和变更记录；
- 在 PROJECT_JOURNAL 留下真实日期、验证结果和证据路径；
- 如果来自用户测试，更新对应 UAT 条目的回归和复验状态。

### 18.3 固定编号

- 业务需求：BR-xx
- 功能模块：Fxx
- 架构决策：ADR-xxx
- API：API-Fxx-xxx
- 测试：TC-Fxx-xxx
- 截图：SS-Fxx-xxx
- 论文图：FIG-章-序号
- 论文表：TAB-章-序号
- 预测实验：EXP-FC-xxx
- AI实验：EXP-AI-xxx
- 数据库迁移：V序号__说明.sql

编号一旦进入已验收文档不得复用。

### 18.4 完成定义

“功能完成”必须同时满足：

1. 可在干净环境启动；
2. 数据库迁移可执行；
3. 前后端和 AI Schema 一致；
4. 正常、异常、权限、状态用例通过；
5. 错误处理和日志可追踪；
6. README/接口/测试/追踪矩阵已更新；
7. 截图来自当前运行版本；
8. 不影响已验收闭环。

少一项只能标记“开发中”，不能标记完成。

### 18.5 变更控制

凡涉及以下内容必须先写 ADR：

- 增删角色或核心模块；
- 更换 Spring/FastAPI 边界；
- 更换数据库、预测模型、LLM任务或关键指标；
- 改变核心表关系、API字段、状态机；
- 扩大对账、ERP接入或AI自动执行范围；
- 修改论文中的核心创新点。

变更说明必须同步列出对代码、SQL、数据、实验、测试、图表、论文和答辩的影响。

| 第11周 | 发布与答辩 | 部署、PPT、讲稿、彩排和备份 |

## 最终验收红线

- 至少一条 BCL-01 在干净环境、四角色下完整运行；
- AI 永远不能跳过校验和人工确认修改业务；
- XGBoost 只做数值预测，LLM 不冒充预测模型；
- 预测与 AI 实验全部可由原始数据和脚本复现；
- 模拟数据、回放和降级模式有明确标签；
- 供应商无法访问其他供应商数据；
- 核心状态不能非法跳转，收货和库存写入保持事务一致；
- 论文不出现项目中不存在的功能、算法、表、实验和截图；
